# Amazon SQS: Queue Types, Internal Mechanics & Limits

## Key Concepts

- **Amazon SQS (Simple Queue Service):** Fully managed distributed message queuing service designed to decouple microservices, buffer workloads, and absorb burst traffic.

- **Two Primary Queue Types:**

    - **Standard Queues:** Default queue type offering nearly unlimited throughput, **at-least-once delivery**, and **best-effort ordering**.

    - **FIFO Queues (First-In, First-Out):** Guarantees **strictly preserved message ordering** and **exactly-once processing** within message groups at a defined throughput limit. Must end with the `.fifo` suffix.

- **Why Are They Different?** They represent a classic distributed systems trade-off between **throughput** and **ordering/deduplication guarantees**. Standard queues favor massive distributed horizontal scale; FIFO queues maintain distributed partition coordination using ordered log partitions.

- **Core Parameters:**

    - **Visibility Timeout:** Duration (0s to 12h, default 30s) a message is hidden from other consumers while being processed by one worker.

    - **Retention Period:** 1 minute to 14 days (default 4 days).

    - **Payload Size:** Max **256 KB** per message. Larger messages use S3 pointers via the SQS Extended Client Library.

## Strong Answers / Talking Points

### 1. Architectural Comparison: Standard vs. FIFO Queues

|**Dimension**|**Standard Queue**|**FIFO Queue**|
|---|---|---|
|**Ordering**|**Best-effort** (messages may arrive out of sequence).|**Strict FIFO** within the same `MessageGroupId`.|
|**Delivery Model**|**At-least-once** (network retries / multi-node sync can produce duplicates).|**Exactly-once processing** (duplicates suppressed within 5-min window).|
|**Throughput**|**Nearly unlimited** transactions per second (TPS).|Base: **300 TPS** (up to 3,000 msg/s with batching). High Throughput Mode: up to 30,000+ msg/s batched.|
|**Cost**|Lowest cost tier ($0.40 per 1M requests).|Slightly higher (~$0.50 per 1M requests).|
|**Queue Name**|Alphanumeric (e.g., `orders-queue`).|**Must end with `.fifo`** (e.g., `orders-queue.fifo`).|
|**Best For**|Decoupling workloads where order doesn't matter (image resizing, email dispatch, log ingestion).|Order-sensitive state machines (financial transactions, sequential inventory updates, ticket booking).|

### 2. Under the Hood of SQS FIFO: Groups & Deduplication

- **`MessageGroupId` (Concurrency Key):**

    - Defines the logical sequence/stream within the queue.

    - SQS guarantees ordering strictly **per message group ID**, not globally across the entire queue.

    - Messages with _different_ `MessageGroupId` values can be consumed concurrently in parallel by distinct consumers.

    - _Best Practice:_ Set `MessageGroupId` to the entity boundary (e.g., `accountId`, `orderId`) to allow parallel processing across customers without sacrificing sequential execution per customer.

- **`MessageDeduplicationId` (Idempotency Window):**

    - Unique token generated by the producer or calculated via SQS content-based SHA-256 hashing.

    - SQS ignores any message sent with the same deduplication ID within a **5-minute sliding window**.

### 3. SQS Polling Mechanics & Cost Optimization

- **Short Polling (`WaitTimeSeconds = 0`):**

    - The SQS request polls a subset of storage servers and returns immediately, even if the queue is empty.

    - Generates high volumes of empty response API calls, significantly increasing AWS bills.

- **Long Polling (`WaitTimeSeconds = 1 to 20`):**

    - The connection stays open up to 20 seconds waiting for a message to enter the queue.

    - Queries all storage servers; returns immediately when messages arrive.

    - Eliminates empty receives, slashes billable requests, and minimizes consumer latency.

### 4. Hard Limitations & Quotas

- **Maximum Payload:** **256 KB** per message. Billed in 64 KB increments (a 256 KB message counts as 4 billable requests).

- **Batching Limit:** Maximum **10 messages** or **256 KB total** per send/receive/delete batch API call.

- **In-Flight Messages Limit:** Up to **120,000** messages (messages received by consumers but not yet deleted or timed out). Exceeding this returns an `OverLimit` error.

- **Message Delay / Delivery Delay:** Maximum **15 minutes**.

## Code Snippets / Examples

### 1. Producing to a FIFO Queue with Deduplication (Node.js / SDK v3)

```typescript
import { SQSClient, SendMessageCommand } from "@aws-sdk/client-sqs";

const sqs = new SQSClient({});

export async function sendOrderedTransaction(userId: string, txId: string, payload: object) {
  const command = new SendMessageCommand({
    QueueUrl: "https://sqs.us-east-1.amazonaws.com/123456789012/transactions.fifo",
    MessageBody: JSON.stringify(payload),
    // Ensures all transactions for this user are processed strictly in order
    MessageGroupId: `USER#${userId}`,
    // Deduplicates retried network requests within a 5-minute window
    MessageDeduplicationId: txId,
  });

  await sqs.send(command);
}
```

### 2. AWS SAM Template: FIFO Queue with Dead-Letter Queue (DLQ)

```yaml
AWSTemplateFormatVersion: '2010-09-09'
Transform: AWS::Serverless-2016-10-31
Description: Production SQS FIFO with DLQ and High Throughput Mode

Resources:
  # Dead Letter Queue for failed FIFO messages
  TransactionDLQ:
    Type: AWS::SQS::Queue
    Properties:
      QueueName: transactions-dlq.fifo
      FifoQueue: true
      MessageRetentionPeriod: 1209600 # 14 days

  # Main Processing FIFO Queue
  TransactionMainQueue:
    Type: AWS::SQS::Queue
    Properties:
      QueueName: transactions.fifo
      FifoQueue: true
      ContentBasedDeduplication: true
      DeduplicationScope: messageGroup
      FifoThroughputLimit: perMessageGroupId
      VisibilityTimeout: 60
      ReceiveMessageWaitTimeSeconds: 20 # Long polling enabled
      RedrivePolicy:
        deadLetterTargetArn: !GetAtt TransactionDLQ.Arn
        maxReceiveCount: 3 # Route to DLQ after 3 failures
```
